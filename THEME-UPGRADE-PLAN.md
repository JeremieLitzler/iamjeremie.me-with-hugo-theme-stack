## ⚠️ Upstream internals that changed, not just paths

These affect _how_ several overrides need to be rewritten, not just _where_ they live:

- **`helper/image` partial's contract was completely redesigned.**
  - Old signature: `partialCached "helper/image" (dict "Context" . "Type" "article") .RelPermalink "article"` → auto-resolves the page's `image` front-matter field (or `featuredImageField`) and falls back to `defaultImage.<type>` config; returns `{exists, permalink, resource, isDefault}`.
  - New signature: `partial "helper/image" (dict "Image" .Params.image "Resources" .Resources "Context" .)` → the caller must pass the image path explicitly; returns `{Resource, Permalink, Height, Width}` (capitalized keys) and has **no `defaultImage` fallback at all** (`defaultImage` doesn't exist in v4's default params). Every override that calls this helper (`header.html`, `article-list/{default,compact,tile}.html`, `list.html`, `_default/archives.html` (via tile), `miscellaneous/taxonomy-cloud-page.html`) needs its call site rewritten to the new contract.
- **`article/components/header.html` and `details.html` were unified** for single-article and list contexts via an explicit `(dict "Page" . "IsList" true/false)` parameter, instead of two separate files. This is the clean fix for the exact problem the current `header-from-article-list.html` / `details-from-article-list.html` duplication and the `.Scratch.Set "parentIsArticle"` / `"isHome"` workaround exist to paper over (see the `25/08/23` comment in `header.html`).
  - **Decided: adopt.** Fold our h1/h2 heading-level customization and the `pageIndex` lazy-load trick into the single `header.html`/`details.html` pair, keyed off the new `IsList` flag, and delete the two `-from-article-list.html` files and the scratch-based workaround. Produces identical HTML output to today, with less code.
- **`mermaid.html` is already effectively at v4.0.3.** The current override matches the new theme's file almost byte-for-byte (only whitespace differs) — it looks like this feature was hand-ported ahead of this upgrade. After the swap this override becomes redundant; I'll
  drop it and let the vendored v4 file serve directly, unless you know of a reason to keep a local copy.
- **Theme i18n format changed from YAML to TOML**, and three custom-ish keys the current overrides depend on were dropped upstream (see "New file needed").

## `relcanonical` → v4 native `canonicalUrl`?

Checked all 86 uses: every single `relcanonical:` value in front matter is already a full
absolute URL (`https://…`) — there are zero relative values. Our current template applies
`relLangURL` to that value, but `relLangURL` is a no-op on an already-absolute URL (it only
prefixes a scheme/host when one is missing), so it produces byte-identical output to v4's
native handling, which just prints `.Params.canonicalUrl` raw with no URL function at all.

So mechanically, **yes** — renaming the front-matter key (`relcanonical:` → `canonicalUrl:`)
across the 86 files and switching the template to `.Params.canonicalUrl` would be a
behavior-preserving find-and-replace, and it means adopting v4's own head.html canonical
handling verbatim instead of maintaining our own.

One wrinkle: two of those 86 files are articles *about* this exact custom field —
`content/post/2024-03/how-to-add-cannonical-url-to-a-hugo-blog/index.md` and
`content/post/2024-08/good-seo-with-hugo/index.md` — their body text explains "I named the
canonical `relcanonical`" and shows template code using `.Params.relcanonical`. A blind
find-and-replace would also rewrite that prose/code-sample content, which is a documentation
decision (leave it as a historical record of what you did, vs. update it to match the new
name), not something I'd want to just do silently.

**Decided: proceed with the replacement.** Rename the front-matter key everywhere (84
straightforward files via find-and-replace) and switch `head.html` to `.Params.canonicalUrl`.
For the two tutorial articles, add a `{{% blockcontainer %}}` note (not a blind text rewrite)
stating that the former `relcanonical` param was used until the v4 theme upgrade — keeps the
articles historically accurate without editing their explanatory prose/code samples.

## `article.*` v4 params — what they do (no action needed unless you want to enable them)

- **`article.headingAnchor`** (bool, default `false`): shows a small anchor link (🔗-style)
  next to every heading, letting readers copy a direct link to that section. This is exactly
  the `{{- if site.Params.Article.HeadingAnchor -}}<a class="header-anchor">…` branch already
  sitting unused in `render-heading.html` today (that override is a no-op precisely because
  this flag has always been off). Turning it on requires no template change, just setting the
  param. **Decided: turn this on** (`headingAnchor = true` in `params.toml`) — since
  `render-heading.html` is otherwise a no-op override, I'll drop it entirely and let this flag
  activate through the vendored v4 file directly.
- **`article.toc`** (bool, default `true` in v4): the site-wide default for whether an
  article's table of contents renders, combined (AND) with the page's own `toc` front-matter
  override and with whether the `"toc"` widget is present in `[[widgets.page]]` — which your
  `params.toml` already declares. So this is effectively already "on" via theme defaults once
  we're on v4 (Hugo merges the theme's own `config/_default/params.toml` in as defaults
  beneath the project's), no config change needed to keep today's TOC behavior.
- **`article.list.showTags`** (bool, default `false`): when true, shows each article's tag
  pills under its entry in list views (homepage, section/category pages) — purely additive,
  off by default, matching current behavior.
- **`article.alertIcon`** (map of emoji per callout type: note/tip/important/warning/caution):
  configures the icons for a **new v4 feature** — native GitHub-style Markdown alert
  blockquotes (`> [!NOTE] …`, `> [!TIP] …`, etc.), rendered by a new render hook
  (`_markup/render-blockquote.html`) that v3 didn't have at all. Worth noting because it's
  conceptually similar to what your `shortcodes/blockcontainer.html` shortcode already does by
  hand. **Decided: not touching this now** — filed as
  [#10](https://github.com/JeremieLitzler/iamjeremie.me-with-hugo-theme-stack/issues/10) to
  evaluate later whether to migrate existing content off the shortcode.

## Config changes (`config/_default/params.toml`)

- `[sidebar.avatar]` table (`enabled`/`local`/`src`) → v4 wants `avatar` as a plain string path. Current: `src = "img/profilepic-400w.jpg"` → new: `avatar = "img/profilepic-400w.jpg"`.
- `[imageProcessing.cover] enabled = true` → v4 has no `cover` key; nearest equivalents are `[imageProcessing.thumbnail].enabled` (used for small square crops like list/tile/archives) and `[imageProcessing.content]` (used for in-article resized images, already present). Since our overrides read `.Page.Site.Params.imageProcessing.cover.enabled` directly in several places (details/list/tile/header), those reads need to switch to whichever new key matches the context, or we keep reading a `cover` key we define ourselves (Hugo params are free-form, nothing stops us keeping `imageProcessing.cover` as our own key going forward — simplest, lowest-risk option, since nothing upstream reads it either way).
- `[imageProcessing.content] enabled = true` → v4 also wants `widths = [...]` (defaults to `[800, 1600, 2400]`); not currently set, will inherit the default unless we want our own 360/600/1024 breakpoints reflected here too.
- `[defaultImage.opengraph]` → not present in v4's default params at all; need to confirm during implementation whether the opengraph partial still reads it (if the site's `head/opengraph` templates aren't overridden, they're 100% stock v4 and I'll check what key, if any, replaced it before removing this section).
- Everything else (`favicon`, `custom_css`, `article.license`, `widgets.*`, `comments.*`, `opengraph.twitter`, `colorScheme`) is compatible as-is.
- `[cookies]` GDPR consent section: **not adding** it, per your feedback — analytics stays disabled as it is today, not gated behind a consent banner.
- `article.headingAnchor = true` — **decided: turning this on** (see dedicated section above).
- `article.toc`, `article.list.showTags`, `article.alertIcon` — leaving unset (v4 defaults apply); `alertIcon` tracked separately in [#10](https://github.com/JeremieLitzler/iamjeremie.me-with-hugo-theme-stack/issues/10).
- `canonicalUrl` replaces `relcanonical` project-wide (front matter rename across 84 files + hand-edited notes in the 2 tutorial articles + `head.html` switched to the native param) — see dedicated section above.

## Found and fixed during implementation (not in the original plan)

- **`defaultImage.opengraph` fallback needed a small override.** v4's stock
  `head/opengraph/provider/base.html` dropped the `defaultImage` fallback entirely (it only
  reads the page's own `.Params.image` now). Added `layouts/_partials/head/opengraph/provider/base.html`
  restoring the old fallback-to-profile-picture behavior for pages with no image of their own,
  so `config/_default/params.toml`'s `[defaultImage.opengraph]` section didn't need to change.
- **SVG featured images broke the build.** v4's new `helper/image` partial returns a `Resource`
  for SVGs too (the old one deliberately excluded them), so the manual `.Resize`/`.Fill` calls
  in `header.html`, `list.html`, and `taxonomy-cloud-page.html` needed an explicit
  `reflect.IsImageResourceProcessable` guard before resizing — otherwise Hugo errors on any
  page whose featured image is an `.svg` (several `.NET`/tooling articles use SVG logos).
- **`relcanonical` file count was wrong in the original research** (see Status note above) —
  86 was actually `relcanonical` OR `seoNoIndex` combined; only 14 files used `relcanonical`.
