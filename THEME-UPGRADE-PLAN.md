# Theme upgrade plan — hugo-theme-stack v3.34.1 → v4.0.3 (issue #9)

This file exists purely for review: it lists every step I'll take and every customization I found while comparing `themes/hugo-theme-stack` (currently vendored v3.34.1) against `layouts/` (the site's overrides) and against the real v4.0.3 theme source (cloned to a scratch dir for comparison, not committed). Please check the inventory below for anything missing before I start editing files. This file will be deleted before the PR is opened (or kept if you'd rather have it as a record — your call).

## Steps I'll take

1. Delete `themes/hugo-theme-stack/` and replace it with the v4.0.3 tag source (`https://github.com/CaiJimmy/hugo-theme-stack`, tag `v4.0.3`), keeping the vendored-copy approach (no git submodule, no Hugo Modules).
2. Move every real customization in `layouts/` to the new template paths v4.0.3 uses:
   1. `layouts/partials/**` → `layouts/_partials/**`,
   2. `layouts/_default/_markup/*` → `layouts/_markup/*`,
   3. `layouts/_default/{list,archives}.html` → top-level,
   4. `layouts/index.html` → `layouts/home.html`
3. Re-merging each file's customization against the new upstream version where the internals changed (see inventory below — several theme internals were rewritten, not just renamed).
4. Delete the no-op override `layouts/_default/_markup/render-heading.html` (identical to both old and new theme — customizes nothing).
5. Delete the dead files `layouts/_default/_markup/render-image-webp.html` and `layouts/partials/image-converter.html` (unreferenced by anything after the theme swap).
6. Add a new `i18n/en.toml` at the project root with the three translation keys v4.0.3 dropped that the `tag-cloud`/`categories` widgets and the taxonomy-cloud page still need (`accessibleLabel`, `allDivParagraph`, `allDivLinkText` for both widgets, plus the `taxoMisc.searchForm.*` block) — see "New file needed" below.
7. Update `config/_default/params.toml` to the v4 schema: `sidebar.avatar` (table → plain string path), `imageProcessing.cover` → `imageProcessing.thumbnail`/`content`, and carry over `defaultImage.opengraph` behavior (removed as a generic key in v4 — needs a per-file check, see "Config changes" below).
8. Delete `.github/workflows/update-theme.yml` (references Hugo Modules and the old v3 module path; inconsistent with vendoring the theme folder directly, and there's no `go.mod` so it's already a no-op today).
9. Run `hugo --gc --minify` locally, fix build errors/warnings, then spot-check rendered HTML for home, an article, an archives page, the search page, and a taxonomy page against the current `public/` output (canonical tag, `noindex`, heading levels, avatar/cover images, mermaid diagrams, widgets).
10. Keep this file as a record.

## ⚠️ Upstream internals that changed, not just paths

These affect _how_ several overrides need to be rewritten, not just _where_ they live:

- **`helper/image` partial's contract was completely redesigned.**
  - Old signature: `partialCached "helper/image" (dict "Context" . "Type" "article") .RelPermalink "article"` → auto-resolves the page's `image` front-matter field (or `featuredImageField`) and falls back to `defaultImage.<type>` config; returns `{exists, permalink, resource, isDefault}`.
  - New signature: `partial "helper/image" (dict "Image" .Params.image "Resources" .Resources "Context" .)` → the caller must pass the image path explicitly; returns `{Resource, Permalink, Height, Width}` (capitalized keys) and has **no `defaultImage` fallback at all** (`defaultImage` doesn't exist in v4's default params). Every override that calls this helper (`header.html`, `article-list/{default,compact,tile}.html`, `list.html`, `_default/archives.html` (via tile), `miscellaneous/taxonomy-cloud-page.html`) needs its call site rewritten to the new contract.
- **`article/components/header.html` and `details.html` were unified** for single-article and list contexts via an explicit `(dict "Page" . "IsList" true/false)` parameter, instead of two separate files. This is the clean fix for the exact problem the current `header-from-article-list.html` / `details-from-article-list.html` duplication and the `.Scratch.Set "parentIsArticle"` / `"isHome"` workaround exist to paper over (see the `25/08/23` comment in `header.html`).
  - **Proposal:** fold our h1/h2 heading-level customization and the `pageIndex` lazy-load trick into the single `header.html`/`details.html` pair, keyed off the new `IsList` flag, and delete the two `-from-article-list.html` files and the scratch-based workaround. This produces identical HTML output to today, with less code.
- **`mermaid.html` is already effectively at v4.0.3.** The current override matches the new theme's file almost byte-for-byte (only whitespace differs) — it looks like this feature was hand-ported ahead of this upgrade. After the swap this override becomes redundant; I'll
  drop it and let the vendored v4 file serve directly, unless you know of a reason to keep a local copy.
- **Theme i18n format changed from YAML to TOML**, and three custom-ish keys the current overrides depend on were dropped upstream (see "New file needed").

## New file needed: `i18n/en.toml`

v4.0.3 simplified `widget.tagCloud`/`widget.categoriesCloud` to a bare `title` string and removed `accessibleLabel`, `allDivParagraph`, and `allDivLinkText` entirely; it also dropped the `taxoMisc` block used by `taxonomy-cloud-page.html`. Without a project-level override, `{{ T "widget.tagCloud.accessibleLabel" }}` etc. render blank. I'll add a project `i18n/en.toml` carrying forward the current wording (title with the `{{ .MaxInCloud }}` count, the accessible label, the "view all" paragraph/link, and the `taxoMisc.searchForm` strings).

## Config changes (`config/_default/params.toml`)

- `[sidebar.avatar]` table (`enabled`/`local`/`src`) → v4 wants `avatar` as a plain string path. Current: `src = "img/profilepic-400w.jpg"` → new: `avatar = "img/profilepic-400w.jpg"`.
- `[imageProcessing.cover] enabled = true` → v4 has no `cover` key; nearest equivalents are `[imageProcessing.thumbnail].enabled` (used for small square crops like list/tile/archives) and `[imageProcessing.content]` (used for in-article resized images, already present). Since our overrides read `.Page.Site.Params.imageProcessing.cover.enabled` directly in several places (details/list/tile/header), those reads need to switch to whichever new key matches the context, or we keep reading a `cover` key we define ourselves (Hugo params are free-form, nothing stops us keeping `imageProcessing.cover` as our own key going forward — simplest, lowest-risk option, since nothing upstream reads it either way).
- `[imageProcessing.content] enabled = true` → v4 also wants `widths = [...]` (defaults to `[800, 1600, 2400]`); not currently set, will inherit the default unless we want our own 360/600/1024 breakpoints reflected here too.
- `[defaultImage.opengraph]` → not present in v4's default params at all; need to confirm during implementation whether the opengraph partial still reads it (if the site's `head/opengraph` templates aren't overridden, they're 100% stock v4 and I'll check what key, if any, replaced it before removing this section).
- Everything else (`favicon`, `custom_css`, `article.license`, `widgets.*`, `comments.*`, `opengraph.twitter`, `colorScheme`) is compatible as-is.
- Not required, but available if wanted: new `[cookies]` GDPR section, `article.headingAnchor`, `article.toc`, `article.list.showTags`, `article.alertIcon` — I'll leave these at their v4 defaults (i.e., not add them) unless you want them turned on.
